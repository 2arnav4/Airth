01 The product

A job here is a unit of background work a server owes someone: send a welcome email, render an invoice PDF, resize an upload. Websites queue this work instead of doing it during a request. Conveyor is the operator's screen for that queue.

Every job carries five required fields — id, title, type, status, createdAt — plus two additions: priority (0–10) and version, which exists purely to catch stale writes.

What the dashboard does

CapabilityWhere it lives
Create a jobForm → POST /jobs; status is never client-supplied
List and filter by statusGET /jobs?status=, newest first
Counts per statusGET /jobs/stats, a single GROUP BY
Advance a jobPATCH /jobs/:id/status, only along legal transitions
Delete a jobDELETE /jobs/:id → 204, or 404 if already gone
Loading and error statesSkeleton rows, an error banner, a conflict notice

02 One request, end to end

A click on Start passes through five checkpoints. Each one rejects what the one above it cannot see, and only the last one is impossible to bypass.

Browser Only renders buttons for legal transitions — a completed job shows none convenience
ParseUUIDPipe :id must be a real UUID, so Postgres never receives junk 400
ValidationPipe Body must contain a known status and nothing else (forbidNonWhitelisted) 400
JobsController Route, status code, reads If-Match. No business rules —
JobsService Asks the transition map which statuses may become the requested one —
Postgres UPDATE … WHERE id = $1 AND status IN ($2) — the check is the write 200 / 409 / 404
Why it's layered this way

React can be skipped with curl. The pipes can't be skipped over HTTP. The service rule can only be skipped with direct SQL access. The job_status enum and the pending default can't be skipped at all.

03 Two tabs, one job

Both tabs show the job as pending. Both click Start within the same millisecond. Exactly one may win, and the loser must be told why rather than silently overwriting the winner.

The fix is three lines

const result = await this.jobsRepository.update(
  { id, status: In(allowedFrom) },   // the condition
  { status: next },                  // the change
);

Which Postgres executes as one atomic statement:

UPDATE jobs SET status = 'running', version = version + 1
WHERE id = $1 AND status IN ('pending');

The first request to reach the row matches and changes one row. The second evaluates status IN ('pending') against the already updated row, matches nothing, and reports affected = 0. There is no window between checking and writing, because they are the same statement.

Reading the outcome

Rows changedMeaningResponse
1Won the race; the fresh row is read back and returned200 OK
0Job exists, wrong state — lost the race, or the job is terminal409 Conflict
0Job exists, but If-Match named an older version412 Precondition Failed
0No row with that id at all404 Not Found
Not a lock

This is an atomic conditional update (compare-and-set), not SELECT … FOR UPDATE. A pessimistic lock earns its cost when the decision needs data you must read and compute first — a bank balance minus a withdrawal. Here the whole condition fits in the WHERE clause, so a lock would add round trips and buy nothing.

scripts/race-test.ts proves it: create a pending job, fire five concurrent PATCHes with Promise.all, and assert exactly one 200, four 409s, and a final status of running. It does not assert which request wins — arrival order isn't controllable, and correctness doesn't depend on it.

07 Decisions worth defending

DecisionReasoningCost
Conditional UPDATE over a row lockThe entire rule fits in a WHERE clauseLosers must refetch rather than wait their turn
UUID primary keyUnguessable; any instance can mint one; leaks no row count16 bytes instead of 4
Postgres enum + pending defaultInvalid statuses are impossible even from raw SQLAdding a status needs a migration, not just a code edit
Explicit field mapping in the serviceA DTO is a public contract; an entity is private storage. One must not silently become the otherTwo edits to add a field instead of one
Migrations, never synchronizeSchema changes are reviewable, ordered and reversibleA CLI step in every deploy
Statuses are lowercase onlyRUNNING is rejected; the API doesn't guess what the client meantClients must match the enum exactly
A running job can be deletedAn operator's dashboard shouldn't refuse to remove a stuck jobWork in progress can vanish; refusing with 409 is the other reasonable call
No paginationRight-sized for the assignment's data volumeNeeds limit/cursor before real use
Bun as runtime and package managerOne tool; fast installs; runs TypeScript directlyLess trodden path than Node for Nest, so fewer answers when something breaks

With more time

Pagination on GET /jobs; a real worker process that picks up pending jobs with FOR UPDATE SKIP LOCKED instead of a human clicking Start; an idempotency key on create so a double-click can't make two jobs; a shared types package so Job is declared once; Swagger for a browsable route list; and a retry path that creates a new job linked to the failed one rather than reviving a terminal row.
